# /qa:automate-functional-tests

Automate functional test cases by implementing executable Java test code using the Tradu Test Automation Framework, reviewing code quality, and applying fixes.

## Input

Argument: `<path-to-functional-tests.md>` — a file generated by `/qa:functional-tests` containing test cases prefixed with `### TC-FUNC`.

Example: `/qa:automate-functional-tests .claude/qa/20260121-order-flow/functional-tests.md`

**Optional flags** (appended after the file path):
- `--skip-exploration` — Skip Phase 0 UI exploration entirely (use css/xpath locator strategies)
- `--reuse-exploration` — Skip Phase 0 but reuse existing `{OUTPUT_DIR}/exploration-*.yaml` files from a previous run

## Prompt Templates

The detailed prompts for each agent are in the `automate-functional-tests/references/` folder:
- **`references/exploration-prompt.md`** — Prompt for UI exploration sub-agent (Phase 0)
- **`references/automation-prompt.md`** — Prompt for qa-automation-architect (Phase 1)
- **`references/review-prompt.md`** — Prompt for qa-code-reviewer (Phase 2)
- **`references/fix-prompt.md`** — Prompt for qa-automation-architect fix pass (Phase 3)

Read the relevant prompt template before spawning each agent.

---

## Execution Instructions

Follow these phases in order. Wait for each phase to complete before starting the next. If any sub-agent does not return within 10 minutes, report the timeout to the user and skip to the next phase (or Step Final if Phase 1 timed out).

Set `OUTPUT_DIR` to the parent directory of the input file. If `OUTPUT_DIR` already contains `automation-summary.md` or `code-review-report.md` from a previous run, warn the user: "Previous run output detected in {OUTPUT_DIR}. Files will be overwritten." Continue.

---

### Step 0: Validate Input

1. Parse the command argument: extract the file path and any flags (`--skip-exploration`, `--reuse-exploration`)
2. Verify the file exists — if not: `"File not found: {path}. Usage: /qa:automate-functional-tests <path-to-functional-tests.md>"`
3. Count test cases (lines matching `### TC-FUNC`) — if zero, report error and stop
4. Validate input format: check that each test case has at minimum a `**Priority:**` line and a `**Interface:**` line. If >50% of test cases are missing these markers, warn the user: "Input file may not be in /qa:functional-tests output format. Proceeding, but results may be incomplete." Continue regardless.
5. Categorize tests by interface type (count lines matching each):
   - `**Interface:** UI-WEB` or `**Interface:** UI-` → UI tests
   - `**Interface:** BE-REST` → REST API tests
   - `**Interface:** BE-FIX` → FIX protocol tests
   - `**Interface:** BE-WEBSOCKET` → WebSocket tests
   - `**Interface:** INTEGRATION-` → Integration tests
6. Report the breakdown to the user
7. If total tests > 20, plan consecutive chunks of 20 tests each (exactly 20 or fewer is a single pass; 21+ triggers chunking — 20 is the practical limit per chunk as larger chunks degrade output quality)
8. If UI-WEB tests detected and `--skip-exploration` is NOT set:
   - Check if the project has a `.claude/PROJECT_TEST_CONTEXT.yaml` with a `frontend_component_paths` section
   - If found, use those paths for `{FRONTEND_COMPONENT_PATHS}` in prompts
   - If not found, ask the user: "UI tests detected. Please provide the frontend component paths where `data-testid` attributes should be added (e.g., `apps/web/dashboard/src/components/`), or create a `.claude/PROJECT_TEST_CONTEXT.yaml` file with a `frontend_component_paths` section. You can also skip with `--skip-exploration`."
   - Store the resolved paths for use in Phase 0 and Phase 1 prompts

---

### Phase 0: UI Exploration (only if UI-WEB tests detected)

Skip if no UI-WEB tests exist, or if user passes `--skip-exploration` / `--reuse-exploration`.

**Concurrency note**: Playwright MCP tools are session-level — do not run other Playwright-dependent skills concurrently with Phase 0.

**If `--reuse-exploration` is set**: Verify that `{OUTPUT_DIR}/exploration-*.yaml` files exist from a previous run. If none are found, warn the user ("No previous exploration files found in {OUTPUT_DIR}. Falling back to --skip-exploration behavior.") and proceed without exploration data. The Phase 1 agent will fall back to MCP discovery (if Playwright MCP is available in the session) or css/xpath locator strategies.

**Exploration is read-only** — it discovers locators and reports missing `data-testid` attributes but does NOT modify frontend code. The Phase 1 automation agent is responsible for adding missing `data-testid` attributes to frontend components based on the exploration findings.

**Execution model**: Spawn a `general-purpose` sub-agent via Task tool. MCP tools (Playwright) are session-level and inherited by sub-agents automatically.

1. Get the project base URL from project CLAUDE.md (`base_url`) or ask the user
2. Read `automate-functional-tests/references/exploration-prompt.md` for the full prompt template
3. Spawn a `general-purpose` sub-agent via Task tool (no dedicated exploration agent exists) with the exploration prompt, substituting placeholders
4. Wait for the sub-agent to complete
5. **If the sub-agent fails entirely** (error, timeout, or no output files created): Log a warning to the user ("Phase 0 exploration failed. Proceeding without exploration data — Phase 1 will use MCP discovery or css/xpath locators.") and continue to Phase 1 without exploration results.
6. Pass results path to Phase 1 automation agent, which will add missing `data-testid` attributes and implement tests

**If exploration fails or returns no locators for a test case**: Log a warning in `exploration-results.md`, note the affected test IDs, and proceed to Phase 1. The automation agent will fall back to MCP discovery (if available) or css/xpath locator strategies for those tests. Include missing locators in the final summary so the team can add `data-testid` attributes later.

---

### Phase 1: Test Automation

Read `automate-functional-tests/references/automation-prompt.md` for the full prompt template.

**Single pass (total tests <= 20)**: Spawn one `qa-automation-architect` agent with the full input file.

**Chunked (total tests > 20)**: Split into consecutive chunks of 20 tests and process ONE AT A TIME (sequential, not parallel — later chunks must see earlier chunks' output to reuse page objects, service classes, and utilities instead of duplicating them).

#### Chunking Rules

When splitting the input file into chunks:
1. **Split point**: Each `### TC-FUNC` marker starts a new test case boundary
2. **Document header**: Everything before the first `### TC-FUNC` marker (frontmatter, shared preconditions, test data definitions, environment setup notes)
3. **Each chunk gets**: The full document header prepended, followed by 20 consecutive `### TC-FUNC` entries and their content

This ensures chunk 2+ agents have the shared context (data schemas, preconditions, environment) that was defined at the top of the document, not just isolated test cases.

For chunks 2+, append to the prompt: "Review test files created by previous chunks. REUSE existing utilities, page objects, and service classes. Do NOT duplicate."

Only the LAST chunk creates `automation-summary.md`.

**If the agent fails or produces no test files**: Stop and report the error to the user ("Phase 1 automation failed — no test files were generated. Check the agent output above for details."). Do not proceed to Phase 1.5.

---

### Phase 1.5: Compilation Validation

Catch syntax and import errors early — before spending tokens on a code review of broken code.

After Phase 1 completes (all chunks if chunked):

1. Identify the project's test module from pom.xml
2. Run `mvn test-compile` to verify the generated tests compile
3. If compilation fails:
   - Read the Maven error output
   - Fix import errors, missing classes, or type mismatches using the Edit tool
   - Re-run `mvn test-compile`
   - **Max 3 fix attempts.** If compilation still fails after 3 rounds, stop and report the remaining errors to the user with the Maven output. Do not proceed to Phase 2 with broken code.
4. Report compilation status before proceeding to Phase 2

---

### Phase 2: Code Review

Read `automate-functional-tests/references/review-prompt.md` for the full prompt template.

Spawn `qa-code-reviewer` agent (Task tool with `subagent_type: qa-code-reviewer`). Wait for completion.

**If the agent fails or `{OUTPUT_DIR}/code-review-report.md` is not created**: Report the error to the user ("Phase 2 code review failed — no report generated."). Skip Phase 3 and proceed to Step Final with a note that code review was not completed.

After the report is written, read `{OUTPUT_DIR}/code-review-report.md` and extract from YAML frontmatter:
- `verdict`, `quality_score`, `critical_issues`, `major_issues`, `minor_issues`, `suggestions`

Report results to the user.

---

### Phase 3: Implement Fixes

Read `automate-functional-tests/references/fix-prompt.md` for the full prompt template.

1. If zero CRITICAL and zero MAJOR issues → skip this phase, report success (MINOR and SUGGESTION issues are left for manual review to avoid gold-plating and keep automation scope bounded)
2. Otherwise, spawn `qa-automation-architect` agent with the fix prompt to apply all CRITICAL and MAJOR fixes
3. **If the agent fails**: Report the error to the user ("Phase 3 fix agent failed. Review the CRITICAL/MAJOR issues in code-review-report.md and apply fixes manually."). Proceed to Step Final.
4. After fixes complete, re-run `mvn test-compile` to verify fixes didn't break compilation
5. If compilation fails, fix errors directly using Edit tool

---

### Step Final: Summary

Report to the user:

```
Test Automation Complete

Output: {OUTPUT_DIR}
Tests:  {TOTAL} total | UI: {UI} | REST: {REST} | FIX: {FIX} | WS: {WS} | Integration: {INT}
Quality: {verdict} | Score: {quality_score}/10 | Fixed: {critical + major} issues

Files:
  {OUTPUT_DIR}/automation-summary.md — Run commands and setup
  {OUTPUT_DIR}/code-review-report.md — Quality assessment

Next: Review automation-summary.md, run tests, integrate into CI/CD
```

If MINOR or SUGGESTION issues remain, note them.

## Reference

Agents load framework context automatically via their agent definitions (`~/.claude/agents/qa-automation-architect.md`, `~/.claude/agents/qa-code-reviewer.md`). Within the agent-spawning task prompts in Phases 1–3 above, **do NOT re-specify framework rules** in the prompts you build — refer agents to their loaded context for API details, locator strategies, wait patterns, and architecture conventions.

## Framework Standards (cross-cutting) — MAINTAINER REFERENCE ONLY, NOT FOR PROMPTS

> ⚠️ **This block is a human-maintainer cheat-sheet, not a runtime enforcement source.** Do NOT copy these bullets into the prompts you build for `qa-automation-architect` or `qa-code-reviewer`. Both agents already enforce these rules via their loaded context files (`FRAMEWORK_CONTEXT.yaml`, `TEST_PATTERNS.yaml`, `API_TESTING_GUIDE.yaml`, etc.) — restating them in per-invocation prompts wastes tokens and risks the prompt and the context files drifting out of sync.
>
> Use this block to (a) onboard new maintainers, (b) spot-check that the agent context files cover everything the skill cares about, and (c) provide a single place to search when investigating "does the skill still enforce X?".
>
> Both `qa-automation-architect` (Phases 1/3) and `qa-code-reviewer` (Phase 2) enforce these via their loaded context files:

- **Service layer**: ALL API calls via Service classes extending `BaseService`, returning raw `ApiResponse` (never direct HTTP/WebSocket/FIX builder calls in tests).
- **AssertJ only** — no JUnit assertions.
- **Deserialize for assertions** (🔴 CRITICAL) — REST/WebSocket response assertions MUST go through `response.as(Dto.class)` / `asList(Dto.class)` / `message.as(Dto.class)`. **Forbidden in assertion context**: `response.body()`, `JsonNode`, `JsonPath`, `ObjectMapper.readTree`, `org.json.*` (e.g. `JSONObject`, `JSONArray`, `JSONTokener`), `WebSocketResponse.fields()`, `WebSocketResponse.getField(...)`, `WebSocketResponse.rawJson()`. **Carve-outs allowed**: Allure / logging attachments, non-JSON `Content-Type` endpoints, `response.raw().headers()` for header checks. 204/304/empty body → assert only `statusCode()`. FIX protocol is out of scope (tag/value access by design). See `API_TESTING_GUIDE.yaml` → "Error Response Models".
- **No `Thread.sleep()`** — use framework Element waits or Awaitility.
- **UI test preconditions via API** — never UI navigation.
- **Hexagonal architecture** — import only `com.tradu.core.*`; never Playwright / HTTP client / QuickFIX/J directly.
- **Parameterize repetitive tests** — When 2+ test methods share the same arrange-act-assert structure and differ only in input/expected values, combine them into a single `@ParameterizedTest` (`@CsvSource` / `@MethodSource` / `@ValueSource`). Severity 🟡 MAJOR. Carve-out: keep tests separate when each name encodes a semantically distinct scenario (different error category, different domain rule) — parameterization would bury that distinction. See `API_TESTING_GUIDE.yaml` → "Pattern 5: Parameterized Tests".
