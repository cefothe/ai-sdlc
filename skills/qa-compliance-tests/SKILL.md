## Output Directory

**IMPORTANT**: All QA artifacts are stored in the **PROJECT directory**, not the global ~/.claude/ directory.

All test documentation generated by this command should be saved to:
```
.claude/qa/<YYYYMMDD>-<feature-slug>/compliance-tests.md
```

Example: `.claude/qa/20251204-order-execution-flow/compliance-tests.md`

## Your Task

Generate regulatory compliance testing scenarios for MiFID II and other financial compliance frameworks applicable to the feature described by the user.

## Test Types Argument

This command defaults to `--test-types=compliance` but can be overridden to include additional test types:

**Default:** `--test-types=compliance`
**Override examples:**
- `--test-types=compliance,functional` (add functional tests)
- `--test-types=all` (generate all test types)

## Input

The user will provide:
- Feature description or user story
- Specific regulatory requirements (if known)
- Compliance scope (if specified)
- **Optional**: `--test-types` argument (defaults to `compliance`)

## Required Process

1. **Analyze Compliance Requirements**
   - Identify applicable regulations (MiFID II, EMIR, Dodd-Frank, etc.)
   - Determine reporting obligations
   - Assess audit trail requirements
   - Identify risk control mandates

2. **Create Output Directory**
   Create the project QA artifacts directory:
   ```bash
   FEATURE_SLUG=$(echo "$ARGUMENTS" | tr '[:upper:]' '[:lower:]' | tr ' ' '-' | sed 's/[^a-z0-9-]//g')
   OUTPUT_DIR=.claude/qa/$(date +%Y%m%d)-${FEATURE_SLUG}
   mkdir -p ${OUTPUT_DIR}
   ```

3. **Invoke the QA Principal Engineer Agent (Coordinator) - Plan Mode**

   **IMPORTANT**: The qa-principal-engineer will FIRST enter plan mode to create an execution plan.

   Use the Task tool to invoke the qa-principal-engineer agent:

   ```
   Analyze the following feature and create a comprehensive test generation plan:

   Feature: [Feature description]
   Test Types Requested: compliance (or from --test-types argument if provided)

   Requirements:
   1. Enter plan mode FIRST
   2. Parse test-types argument: compliance (default) or user-provided value
   3. Determine which agents to spawn (qa-compliance-engineer, and others if test-types includes them)
   4. Define scope for compliance testing:
      - MiFID II transaction reporting (RTS 22, Article 26)
      - Audit trail completeness and immutability
      - Clock synchronization accuracy (UTC ±100μs)
      - Best execution validation and documentation
      - Position tracking accuracy and reconciliation
      - Risk control effectiveness (pre-trade and post-trade)
      - ARM validator compliance for transaction reports
   5. Write execution plan to ~/.claude/plans/qa-execution-plan.md
   6. Exit plan mode for user approval
   7. After approval, spawn qa-compliance-engineer agent (and others if requested) with isolated context

   COVERAGE REQUIREMENTS:
   - Generate comprehensive compliance test coverage
   - No limits on test case count (generate ALL necessary scenarios)
   - Follow TEST_CASE_BEST_PRACTICES.yaml methodology
   - Reference specific regulatory requirements
   - Reference specific codebase components

   OUTPUT DESTINATION:
   - Compliance tests: ${OUTPUT_DIR}/compliance-tests.md
   ```

4. **Invoke the QA Test Plan Reviewer Agent**
   Use the Task tool to invoke the qa-test-plan-reviewer agent:

   ```
   Review the compliance test scenarios created by the qa-principal-engineer agent.

   Evaluate across these critical dimensions:
   - Regulatory Coverage (MiFID II, EMIR, all applicable regulations)
   - Compliance Validation Completeness (all required fields, deadlines)
   - Risk and Audit Trail Requirements
   - Documentation and Evidence Requirements
   - Regulatory Deadline Compliance
   - Strategic Gaps (missing compliance checks, untested regulations)

   Provide:
   - Executive Summary with overall quality score (1-10) and critical blockers
   - Detailed Findings for each dimension with specific gaps
   - Missing Compliance Scenarios
   - Regulatory Risks not adequately addressed
   - Quality Gate verdict: APPROVED / APPROVED WITH CONCERNS / BLOCKED

   Read the compliance scenarios file at ${OUTPUT_DIR}/compliance-tests.md and provide specific, actionable feedback.

   Save your review to: ${OUTPUT_DIR}/compliance-tests-review.md
   ```

5. **Address Reviewer Findings**
   If the reviewer identifies issues (APPROVED WITH CONCERNS or BLOCKED):

   Use the Task tool to invoke the qa-principal-engineer agent again:

   ```
   Address the following issues identified by the qa-test-plan-reviewer:

   [List of specific issues from reviewer]

   Update the compliance scenarios to:
   - Add missing regulatory requirements
   - Enhance validation checks for compliance
   - Address all CRITICAL and HIGH severity findings
   - Add missing required fields or data points
   - Improve documentation requirements
   - Add missing risk control validations

   Update the compliance scenarios file at ${OUTPUT_DIR}/compliance-tests.md with the improvements.
   ```

6. **Final Review (if needed)**
   If significant changes were made, optionally invoke the reviewer again to validate improvements.

7. **Present Final Output**
   - Present the reviewed and improved compliance scenarios
   - Display the file location: `${OUTPUT_DIR}/compliance-tests.md`
   - Display the review location: `${OUTPUT_DIR}/compliance-tests-review.md`
   - Highlight the review verdict and quality score
   - Note regulatory deadlines and critical requirements
   - Call out any gaps that were addressed
   - Note any remaining concerns
   - Suggest remediation if needed

## Example Scenarios

### CT-001: MiFID II Transaction Reporting Completeness

**Regulatory Requirement:** MiFID II RTS 22, Article 26 - Transaction Reporting

**Test Scenario:**
Execute a representative sample of orders across all asset classes and verify that transaction reports contain all 65 required fields as mandated by MiFID II RTS 22. Submit reports to ARM validator to ensure zero validation errors.

**Test Steps:**
1. Execute 100 orders with the following distribution:
   - FOREX: 40 orders (EURUSD, GBPUSD, USDJPY, etc.)
   - CRYPTO: 20 orders (BTCUSD, ETHUSD)
   - CFD_INDEX: 15 orders (US30, UK100, GER40)
   - CFD_EQUITY: 15 orders (AAPL, TSLA, MSFT)
   - CFD_COMMODITY: 10 orders (GOLD, OIL)
2. Include mix of order types: MARKET, LIMIT, STOP
3. Include both BUY and SELL sides
4. Execute during market hours (proper timestamps)
5. Export transaction reports from OMS
6. Parse reports and validate field population
7. Submit reports to ARM validator
8. Review validator output for errors/warnings

**Required Fields/Data Points:**
- Trading venue: Must be populated with MIC code
- Instrument identification: ISIN/LEI for instrument
- Instrument classification: CFI code
- Buy/sell indicator: BUY or SELL
- Quantity: Number of units/contracts
- Price: Execution price (with correct precision)
- Transaction timestamp: UTC with ±100μs accuracy
- Venue of execution: LP identifier or internal
- Country of branch: ISO country code
- Investment decision maker: LEI or algorithm identifier
- Executing trader: LEI or algorithm identifier
- Order transmission: If applicable, intermediary details
- Client identification: LEI or national ID
- Client capacity: DEAL for principal, AOTC for agent
- Trading capacity: DEAL or MTCH
- Commodity derivative indicator: Y/N
- Securities financing transaction: Y/N

**Validation Criteria:**
- All 65 required fields populated for every transaction
- No null or empty values where required
- Timestamp accuracy within ±100μs of UTC
- Correct data types and formats (ISO codes, LEIs, MICs)
- Price precision matches asset class requirements:
  - FOREX: 5 decimals
  - CRYPTO: 8 decimals
  - CFD: 2 decimals
- Instrument identifiers valid (ISIN check digit validation)

**Pass Criteria:**
- 100% field population across all 100 transaction reports
- Zero validation errors from ARM validator
- Zero validation warnings (best practice)
- Reports generated within 15 minutes of T+1
- All timestamps accurate to ±100μs
- Correct classification codes (CFI, MIC, LEI)
- Reports stored securely for 5+ years (record keeping requirement)

**Documentation Requirements:**
- Transaction report XML/CSV files
- ARM validator output (screenshots or logs)
- Field population analysis report
- Timestamp accuracy verification
- Exception report (if any failures)

**Failure Scenarios:**
- Missing required fields → Non-compliant, risk of regulatory fine
- Incorrect timestamp accuracy → Non-compliant, must fix clock sync
- ARM validator errors → Cannot submit to regulator until resolved
- Late reporting (beyond T+1 + 15min) → Regulatory breach

**Regulatory Impact:**
- Non-compliance: Regulatory fines up to 10% of annual turnover or €5M
- Reporting obligation: Submit corrected reports within specified timeframe
- Audit trail: Maintain evidence of compliance efforts

### CT-002: Audit Trail Immutability Verification

**Regulatory Requirement:** MiFID II Article 25(1) - Record Keeping, EMIR Article 9 - Record Keeping

**Test Scenario:**
Validate that the event sourcing audit trail is immutable, tamper-proof, and produces deterministic replay. Verify that any attempt to modify historical events is detected and prevented.

**Test Steps:**
1. Execute order lifecycle: Submit → Modify → Partial Fill → Modify → Fill
2. Record event IDs for all events (6+ events expected)
3. Export event log entries for this order
4. Verify cryptographic hash chain:
   - Each event contains hash of previous event
   - Root hash verifiable against known good value
5. Attempt to modify historical event (controlled test):
   - Change order quantity in middle event
   - Recalculate hash
6. Replay event stream from snapshot:
   - Load last snapshot
   - Replay all events
   - Compare final state to current state
7. Verify tamper detection:
   - Modified event should break hash chain
   - Replay should detect inconsistency
   - System should reject corrupted log

**Required Fields/Data Points:**
- Event ID: Unique identifier for each event
- Event type: ORDER_SUBMITTED, ORDER_MODIFIED, ORDER_FILLED, etc.
- Event timestamp: Microsecond precision UTC
- Event payload: Complete order data at that moment
- Event hash: Cryptographic hash of this event
- Previous event hash: Hash of preceding event
- Aggregate ID: Order ID or entity ID
- Sequence number: Monotonically increasing

**Validation Criteria:**
- All events captured (no missing state changes)
- Events ordered by sequence number
- Timestamps monotonically increasing (or equal for simultaneous events)
- Hash chain integrity verified
- Deterministic replay: Same inputs → Same final state
- Tamper detection works (modified events flagged)
- No ability to delete or modify historical events via API

**Pass Criteria:**
- Event log contains all state transitions
- Hash chain intact (no broken links)
- Deterministic replay produces identical state (bit-for-bit)
- Tamper attempt detected and rejected
- Error logged when hash mismatch detected
- Read-only access to historical events enforced
- Backup and archive processes preserve integrity

**Documentation Requirements:**
- Event log export (JSON/binary)
- Hash chain verification report
- Replay test results (before/after state comparison)
- Tamper detection test evidence
- Security audit log showing access attempts

**Failure Scenarios:**
- Missing events → Incomplete audit trail, regulatory violation
- Broken hash chain → Potential tampering, investigation required
- Non-deterministic replay → System state corruption possible
- Undetected tampering → Compliance failure, loss of trust

**Regulatory Impact:**
- MiFID II: Must maintain complete, accurate records for 5 years
- EMIR: Must maintain records for 10 years for derivatives
- Auditor access: Regulators can request complete audit trail
- Legal proceedings: Audit trail may be evidence in disputes

### CT-003: Clock Synchronization Accuracy (UTC ±100μs)

**Regulatory Requirement:** MiFID II RTS 25 - Clock Synchronization

**Test Scenario:**
Validate that all system clocks are synchronized to UTC within ±100 microseconds as required by MiFID II for high-frequency trading systems (Category 1 - sub-millisecond latency).

**Test Steps:**
1. Identify reference time source:
   - GPS-synchronized atomic clock, or
   - NIST time server, or
   - National Physical Laboratory (NPL) time service
2. Configure NTP client monitoring on all trading nodes:
   - OMS servers
   - Gateway servers (FIX, REST, WebSocket)
   - Matching engine
   - Market data servers
3. Sample NTP offset every 1 second for 1 hour (3,600 samples)
4. Record:
   - NTP offset (microseconds)
   - NTP stratum
   - NTP jitter
   - NTP delay
5. Analyze results:
   - Calculate percentiles: p50, p95, p99, p100 (max)
   - Identify any outliers >100μs
   - Check for clock drift trends
6. Test leap second handling:
   - Simulate leap second insertion
   - Verify no system crashes or timestamp errors

**Required Fields/Data Points:**
- System hostname: Which server being measured
- Timestamp: When measurement taken
- NTP offset: Difference from reference time (μs)
- NTP stratum: Distance from reference clock (should be ≤3)
- NTP jitter: Clock stability metric
- NTP delay: Round-trip time to time server

**Validation Criteria:**
- 100% of samples within ±100μs of UTC reference
- NTP stratum ≤3 (close to reference clock)
- NTP jitter <50μs (stable clock)
- No clock steps >1ms (gradual slewing only)
- Continuous NTP sync (no sync failures)
- Backup NTP servers configured (redundancy)

**Pass Criteria:**
- All 3,600 samples per node within ±100μs
- Maximum absolute offset <100μs across all nodes
- No NTP sync failures during test period
- Clock drift rate <50μs per hour
- Leap second handled gracefully (no errors)
- Transaction timestamps remain within ±100μs during leap second

**Documentation Requirements:**
- NTP monitoring dashboard screenshots
- Offset distribution histogram (showing <100μs)
- Sync status logs for test period
- Configuration files for NTP daemons
- Reference time source certificate/attestation
- Leap second test results

**Failure Scenarios:**
- Offset >100μs → Non-compliant, must improve time sync
- NTP sync failure → Loss of time synchronization, halt trading
- Clock step >1ms → Timestamp discontinuity, data integrity issue
- Leap second crash → System availability problem

**Regulatory Impact:**
- MiFID II Category 1: ±100μs required (HFT, maker-taker)
- Category 2: ±1ms required (non-HFT)
- Category 3: ±1 second required (non-electronic)
- Non-compliance: Fines, trading restrictions
- Audit: Must provide evidence of synchronization accuracy

### CT-004: Best Execution Validation

**Regulatory Requirement:** MiFID II Article 27 - Best Execution

**Test Scenario:**
Validate that orders are executed at the best available price among all connected liquidity providers, and that best execution reports demonstrate compliance with price improvement and execution quality obligations.

**Test Steps:**
1. Configure test with 5+ connected LPs
2. For 100 MARKET orders (EURUSD):
   - Capture LP quotes at moment of order receipt
   - Record: LP name, BID, ASK, timestamp (μs precision)
3. Execute order via matching engine
4. Record execution details:
   - Execution price
   - Execution venue (which LP)
   - Timestamp of execution
5. Calculate for each order:
   - Best available BID (highest among all LPs)
   - Best available ASK (lowest among all LPs)
   - Execution price vs best available
   - Slippage (pips)
   - Price improvement (if any)
6. Generate best execution report
7. Validate routing decisions:
   - Was best LP selected?
   - If not, was there valid reason (credit limit, connectivity)?

**Required Fields/Data Points:**
- Order ID: Unique identifier
- Symbol: EURUSD, etc.
- Side: BUY or SELL
- Quantity: Order size
- Order timestamp: When order received
- LP quotes snapshot:
  - LP1: BID 1.08500, ASK 1.08520
  - LP2: BID 1.08502, ASK 1.08518 (best ASK for BUY)
  - LP3: BID 1.08498, ASK 1.08522
- Best available price: 1.08518 (for BUY order)
- Execution price: Actual fill price
- Execution venue: Which LP filled the order
- Slippage: Execution - Best available (pips)
- Price improvement: If execution better than best quote

**Validation Criteria:**
- Execution price matches or beats best available quote
- If execution worse: Valid reason documented (e.g., LP timeout)
- Slippage within acceptable thresholds:
  - FOREX: <1 pip average, <2 pips p99
  - CRYPTO: <0.01% average
- Price improvement documented when achieved
- Routing decision justifiable and logged
- Best execution report complete and accurate

**Pass Criteria:**
- 100% of orders have LP quotes captured
- ≥95% of orders executed at or better than best available price
- Average slippage <1 pip for FOREX
- Price improvement achieved in >10% of orders (if market conditions allow)
- Routing decisions documented with rationale
- Best execution report generated automatically
- No unexplained poor executions

**Documentation Requirements:**
- Best execution report (monthly/quarterly)
- Order-by-order execution analysis
- LP quote snapshots at order time
- Slippage analysis with histograms
- Price improvement statistics
- Venue selection justification logs

**Failure Scenarios:**
- Execution worse than best available without reason → Non-compliant
- No LP quotes captured → Cannot demonstrate best execution
- Excessive slippage (>2 pips avg) → Poor execution quality
- Missing best execution report → Regulatory requirement not met

**Regulatory Impact:**
- MiFID II: Must take "sufficient steps" to obtain best execution
- Must monitor execution quality on ongoing basis
- Annual best execution reports required
- Client notification of material changes to execution policy

### CT-005: Position Tracking Accuracy and Reconciliation

**Regulatory Requirement:** MiFID II Organizational Requirements, EMIR Article 11 - Reconciliation

**Test Scenario:**
Validate that internal position tracking matches LP confirmations and external records, ensuring accurate P&L calculation and no position discrepancies that could indicate data loss or system errors.

**Test Steps:**
1. Execute 1,000 round-trip trades (open → close) across:
   - Multiple asset classes
   - Multiple LPs
   - Various order sizes
2. Calculate expected positions independently:
   - Track all FILLS from order execution reports
   - Sum by symbol: BUY fills (+), SELL fills (-)
   - Net position = Total BUY - Total SELL
3. Query system-reported positions:
   - GET /api/v1/positions
   - Extract quantity, side, average entry price
4. Compare expected vs actual:
   - Position quantity match?
   - Position side correct (LONG/SHORT)?
   - Average entry price calculated correctly?
5. Obtain LP confirmations:
   - FIX ExecutionReports
   - LP portal position snapshots
   - End-of-day statements
6. Reconcile system vs LP:
   - Position quantities match?
   - Any unmatched fills?
   - Break investigation for discrepancies
7. Validate P&L calculations:
   - Unrealized P&L: (Current price - Entry price) × Quantity
   - Realized P&L: Sum of closed position P&L
   - Total P&L: Unrealized + Realized
8. Compare calculated vs system-reported P&L

**Required Fields/Data Points:**
- Symbol: EURUSD, BTCUSD, etc.
- Position quantity: Number of units/contracts
- Position side: LONG, SHORT, FLAT
- Average entry price: Weighted average of fill prices
- Current market price: Latest BID (for LONG) or ASK (for SHORT)
- Unrealized P&L: Mark-to-market on open positions
- Realized P&L: Closed position gains/losses
- Total P&L: Sum of unrealized and realized

**Validation Criteria:**
- Position quantity matches order fills (to the unit)
- Average entry price calculated correctly (weighted by quantity)
- System position matches LP confirmation (zero discrepancies)
- Unrealized P&L accurate within ±0.01% (rounding tolerance)
- Realized P&L matches sum of closed trades
- No orphaned fills (executions without corresponding position)
- No phantom positions (positions without executions)

**Pass Criteria:**
- 100% position quantity accuracy (zero discrepancies)
- Average entry price within 1 pip of expected
- P&L calculation within ±0.1% of expected (accounting for fees)
- Daily reconciliation with LPs: 100% match rate
- Break resolution: All discrepancies investigated within 24 hours
- Audit trail supports position history

**Documentation Requirements:**
- Position reconciliation report (daily)
- Discrepancy investigation logs (if any)
- LP confirmation matching report
- P&L calculation verification
- Position snapshot at day end (for audit)

**Failure Scenarios:**
- Position mismatch → Data integrity issue, halt trading until resolved
- P&L incorrect → Client impact, potential financial loss
- Unreconciled breaks → Regulatory concern, operational risk
- Missing LP confirmations → Cannot verify positions

**Regulatory Impact:**
- EMIR: Derivatives positions must be reconciled
- MiFID II: Accurate record-keeping required
- Client reporting: Incorrect positions/P&L → client complaints
- Financial reporting: Incorrect P&L affects firm financials
