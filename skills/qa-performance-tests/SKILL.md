## Output Directory

**IMPORTANT**: All QA artifacts are stored in the **PROJECT directory**, not the global ~/.claude/ directory.

All test documentation generated by this command should be saved to:
```
.claude/qa/<YYYYMMDD>-<feature-slug>/performance-tests.md
```

Example: `.claude/qa/20251204-order-execution-flow/performance-tests.md`

## Your Task

Generate comprehensive performance, load, and stress testing scenarios with measurable objectives and clear pass/fail criteria for the feature described by the user.

## Test Types Argument

This command defaults to `--test-types=performance` but can be overridden to include additional test types:

**Default:** `--test-types=performance`
**Override examples:**
- `--test-types=performance,functional` (add functional tests)
- `--test-types=all` (generate all test types)

## Input

The user will provide:
- Feature description or user story
- Specific performance concerns (if any)
- Expected load characteristics (if specified)
- **Optional**: `--test-types` argument (defaults to `performance`)

## Required Process

1. **Analyze Performance Requirements**
   - Identify critical performance paths
   - Determine latency requirements (<100μs p50 for critical paths)
   - Assess throughput requirements (300K-1M orders/second)
   - Identify resource constraints (CPU, memory, network)

2. **Create Output Directory**
   Create the project QA artifacts directory:
   ```bash
   FEATURE_SLUG=$(echo "$ARGUMENTS" | tr '[:upper:]' '[:lower:]' | tr ' ' '-' | sed 's/[^a-z0-9-]//g')
   OUTPUT_DIR=.claude/qa/$(date +%Y%m%d)-${FEATURE_SLUG}
   mkdir -p ${OUTPUT_DIR}
   ```

3. **Invoke the QA Principal Engineer Agent (Coordinator) - Plan Mode**

   **IMPORTANT**: The qa-principal-engineer will FIRST enter plan mode to create an execution plan.

   Use the Task tool to invoke the qa-principal-engineer agent:

   ```
   Analyze the following feature and create a comprehensive test generation plan:

   Feature: [Feature description]
   Test Types Requested: performance (or from --test-types argument if provided)

   Requirements:
   1. Enter plan mode FIRST
   2. Parse test-types argument: performance (default) or user-provided value
   3. Determine which agents to spawn (qa-performance-engineer, and others if test-types includes them)
   4. Define scope for performance testing:
      - Latency benchmarks (p50, p95, p99, p99.9 percentiles) with <100μs p50 target
      - Throughput capacity (300K-1M orders/second)
      - Stress testing (2x, 5x, 10x normal load)
      - Soak testing (24-48 hours sustained load)
      - Spike testing (sudden traffic bursts)
      - Resource utilization monitoring
      - Aeron back-pressure handling
      - Recovery time measurement
      - Gatling test implementations (Java)
   5. Write execution plan to ~/.claude/plans/qa-execution-plan.md
   6. Exit plan mode for user approval
   7. After approval, spawn qa-performance-engineer agent (and others if requested) with isolated context

   COVERAGE REQUIREMENTS:
   - Generate comprehensive performance test coverage
   - No limits on test case count (generate ALL necessary scenarios)
   - Follow TEST_CASE_BEST_PRACTICES.yaml methodology
   - Include Gatling implementations for load testing
   - Reference specific codebase components

   OUTPUT DESTINATIONS:
   - Performance tests: ${OUTPUT_DIR}/performance-tests.md
   - Gatling implementations: ${OUTPUT_DIR}/gatling/ (Maven project structure)
   ```

4. **Invoke the QA Test Plan Reviewer Agent**
   Use the Task tool to invoke the qa-test-plan-reviewer agent:

   ```
   Review the performance test scenarios created by the qa-principal-engineer agent.

   Evaluate across these critical dimensions:
   - Performance Coverage (latency, throughput, stress, soak, spike testing)
   - HFT-Specific Criteria (p99.9 latency targets, microsecond precision)
   - Measurement Methodology (appropriate tools, accurate metrics)
   - Threshold Appropriateness (realistic targets for HFT systems)
   - Resource Monitoring (CPU, memory, network, back-pressure)
   - Baseline and Regression Detection (comparison points)

   Provide:
   - Executive Summary with overall quality score (1-10) and critical blockers
   - Detailed Findings for each dimension with specific gaps
   - Missing Performance Scenarios
   - Infrastructure Requirements validation
   - Quality Gate verdict: APPROVED / APPROVED WITH CONCERNS / BLOCKED

   Read the performance scenarios file at ${OUTPUT_DIR}/performance-tests.md and provide specific, actionable feedback.

   Save your review to: ${OUTPUT_DIR}/performance-tests-review.md
   ```

5. **Address Reviewer Findings**
   If the reviewer identifies issues (APPROVED WITH CONCERNS or BLOCKED):

   Use the Task tool to invoke the qa-principal-engineer agent again:

   ```
   Address the following issues identified by the qa-test-plan-reviewer:

   [List of specific issues from reviewer]

   Update the performance scenarios to:
   - Add missing performance test types
   - Adjust thresholds to meet HFT standards
   - Enhance measurement methodology where noted
   - Address all CRITICAL and HIGH severity findings
   - Add missing resource monitoring requirements
   - Improve pass/fail criteria specificity

   Update the performance scenarios file at ${OUTPUT_DIR}/performance-tests.md with the improvements.
   ```

6. **Final Review (if needed)**
   If significant changes were made, optionally invoke the reviewer again to validate improvements.

7. **Present Final Output**
   - Present the reviewed and improved performance scenarios
   - Display the file location: `${OUTPUT_DIR}/performance-tests.md`
   - Display the review location: `${OUTPUT_DIR}/performance-tests-review.md`
   - Highlight the review verdict and quality score
   - Note critical performance paths that received special attention
   - Call out infrastructure requirements
   - Suggest monitoring and observability setup
   - Highlight any baseline establishment recommendations

## Example Scenarios

### PT-001: Order Submission Latency Benchmark

**Objective:** Validate end-to-end order submission latency meets sub-millisecond requirement for critical path via FIX protocol.

**Test Configuration:**
- Protocol: FIX 4.4 (lowest latency path)
- Order Type: MARKET (fastest execution)
- Asset: EURUSD (most liquid)
- Quantity: 100,000 (standard lot)
- Load: Single client, sequential orders
- Duration: 10,000 orders
- Measurement: Gateway receipt timestamp → Execution report timestamp
- Component: FIX Gateway → Cluster Relay → OMS → Matching Engine → LP Connector

**Performance Thresholds:**
- p50 latency: <50μs (target), <100μs (maximum acceptable)
- p95 latency: <200μs (target), <500μs (maximum acceptable)
- p99 latency: <500μs (target), <1ms (maximum acceptable)
- p99.9 latency: <2ms (target), <5ms (maximum acceptable)
- Max latency: <10ms (no outliers above this)
- Standard deviation: <100μs

**Measurement Methodology:**
- Tool: JMH (Java Microbenchmark Harness)
- Warm-up: 5,000 iterations (allow JIT compilation)
- Measurement: 10,000 iterations
- JVM flags: `-XX:+UseG1GC -XX:MaxGCPauseMillis=1 -XX:+AlwaysPreTouch` (production settings)
- Histogram: HdrHistogram with 3-significant-digit precision
- Timing: System.nanoTime() for microsecond precision
- Synchronization: Disable during measurement
- Garbage Collection: Monitor and exclude GC pauses from latency measurement

**Pass Criteria:**
- All percentiles (p50, p95, p99, p99.9) meet maximum thresholds
- No latency spikes >10ms during entire test
- Consistent latency across test duration (no degradation)
- Zero order rejections or errors
- Zero timeout events
- Standard deviation within acceptable range
- Latency distribution shows tight clustering (not bimodal)

**Expected Behavior:**
- Latency remains constant throughout test
- No memory allocation in critical path (after warm-up)
- No garbage collection during measurement phase
- CPU utilization <30% (single-threaded)
- No Aeron back-pressure events

**Failure Indicators:**
- Any percentile exceeds maximum threshold
- Latency spikes >10ms
- Increasing latency trend over time
- Bimodal latency distribution
- GC pauses during measurement
- Memory allocation in hot path

**Recovery Validation:**
- Not applicable (benchmark test, no system stress)

### PT-002: Throughput Capacity Test

**Objective:** Validate system handles 300,000 orders/second sustained throughput with acceptable latency under realistic mixed protocol load.

**Test Configuration:**
- Protocols: FIX (50%), REST (30%), WebSocket (20%)
- Order Mix: MARKET (60%), LIMIT (30%), STOP (10%)
- Asset Mix: FOREX (70%), CRYPTO (20%), CFD (10%)
- Load: 1,000 concurrent clients
- Duration: 60 minutes
- Ramp-up: 100 clients/minute (10-minute ramp)
- Target: 300,000 orders/second sustained
- Measurement: Orders submitted vs orders executed, latency distribution

**Performance Thresholds:**
- Throughput: >300,000 orders/second (minimum sustained)
- Error rate: <0.1% (no more than 300 errors/second)
- Average latency: <10ms (across all protocols)
- p95 latency: <50ms
- p99 latency: <100ms
- CPU utilization: <80% (per service)
- Memory growth: <10% over 60-minute duration
- Aeron back-pressure events: <100 total

**Measurement Methodology:**
- Tool: Custom load generator with protocol support
- Metrics collection: Prometheus + Grafana
- Sampling: 1-second intervals
- Latency measurement: Client send → execution report receive
- Resource monitoring: Node exporter, JMX metrics
- Aeron metrics: Publication back-pressure counter

**Pass Criteria:**
- Sustained throughput >300K orders/second for full 60 minutes
- Error rate <0.1% throughout test
- All latency percentiles meet thresholds
- CPU utilization remains <80% per service
- Memory growth <10% (no memory leak)
- No system crashes or service restarts
- No OutOfMemory errors
- Aeron back-pressure events <100
- All orders successfully processed or explicitly rejected

**Expected Behavior:**
- Linear scalability during ramp-up
- Stable throughput at target load
- Consistent latency distribution
- Memory stabilizes after initial ramp (GC maintains steady state)
- CPU utilization plateaus at sustainable level
- No resource exhaustion
- Graceful error handling for legitimate rejections

**Failure Indicators:**
- Throughput drops below 300K orders/second
- Error rate exceeds 0.1%
- Latency increases over time (performance degradation)
- CPU utilization >90% sustained
- Memory growth >10% (potential leak)
- Increasing Aeron back-pressure events
- Service crashes or OOM errors
- Unprocessed orders accumulating

**Recovery Validation:**
- After load test completion, verify system returns to idle state
- Memory released back to baseline (post-GC)
- CPU utilization <10% at idle
- No lingering threads or connections
- All orders processed (queue empty)
- No corrupted state
- Subsequent orders process normally

### PT-003: Stress Test (5x Normal Load)

**Objective:** Validate graceful degradation under extreme load (5x capacity) and verify system remains stable without crashes or data corruption.

**Test Configuration:**
- Target: 1,500,000 orders/second (5x normal capacity)
- Duration: 30 minutes
- Ramp-up: 250K orders/second every 2 minutes
- Protocols: FIX (60%), REST (30%), WebSocket (10%)
- Order Mix: MARKET (80%), LIMIT (20%)
- Monitoring: Resource exhaustion detection, error rates, back-pressure

**Performance Thresholds:**
- System remains operational (no crashes)
- Error rate: Expected to increase, but <50% at peak
- Rejected orders: Clear error codes provided
- Back-pressure: Activated appropriately
- CPU utilization: May reach 100%
- Memory: No OOM errors (bounded allocation)
- Recovery time: <2 minutes to baseline after load removal

**Measurement Methodology:**
- Tool: Custom load generator with aggressive send rates
- Metrics: Focus on stability, not performance
- Error tracking: Categorize rejection reasons
- Resource monitoring: Every second
- Crash detection: Process monitoring

**Pass Criteria:**
- No system crashes or JVM termination
- No data loss (all submitted orders accounted for)
- No state corruption (deterministic replay succeeds)
- Back-pressure activated when queues fill
- Orders rejected with appropriate error codes:
  - BACKPRESSURE
  - THROTTLED
  - INSUFFICIENT_CAPACITY
- System recovers to normal operation after load reduction
- All services remain responsive (no deadlocks)
- Aeron publications handle back-pressure correctly

**Expected Behavior:**
- System accepts orders up to capacity limit
- Beyond capacity: Orders rejected with back-pressure error
- CPU utilization reaches 100%
- Memory usage increases but remains bounded
- Aeron publications return BACK_PRESSURED status
- Cluster consensus maintained
- No leader election during stress (stable cluster)
- Logging remains operational (may buffer)

**Failure Indicators:**
- System crash or JVM OOM
- Data loss or corruption
- Accepted orders not processed
- Silent failures (no error reported)
- Deadlock or complete unresponsiveness
- Leader election during stable stress
- Memory unbounded growth
- Aeron publication failures

**Recovery Validation:**
- Reduce load to baseline (100K orders/second)
- Verify system accepts and processes orders normally
- Latency returns to baseline (<100μs p50)
- CPU utilization drops to <50%
- Memory stabilizes (GC clears buffers)
- Error rate returns to <0.1%
- Back-pressure events cease
- All services healthy

### PT-004: Soak Test (24-Hour Sustained Load)

**Objective:** Validate no memory leaks, resource exhaustion, or performance degradation over extended 24-hour period under sustained load.

**Test Configuration:**
- Load: 200,000 orders/second (60% of capacity)
- Duration: 24 hours
- Protocols: Mixed (FIX 50%, REST 30%, WebSocket 20%)
- Order Mix: Realistic production mix
- Monitoring: Continuous resource tracking, snapshot creation, GC analysis

**Performance Thresholds:**
- Memory growth: <5% per hour (linear growth acceptable for event log)
- CPU utilization: Stable <60% throughout
- Latency: No degradation (p99 remains <1ms)
- Error rate: <0.1% throughout
- Snapshot creation: Completes in <30 seconds every 4 hours
- No OutOfMemory errors
- No connection leaks (stable connection count)

**Measurement Methodology:**
- Tool: Custom load generator with continuous operation
- Metrics: Grafana dashboards with 1-minute resolution
- Heap dump: Every 6 hours for leak analysis
- GC logs: Continuous logging with analysis
- Snapshot: Triggered every 4 hours (6 total)
- Thread dump: Every 6 hours for leak detection

**Pass Criteria:**
- Linear memory growth <5% per hour (acceptable for event sourcing)
- No OutOfMemory errors during 24 hours
- CPU utilization stable (no upward trend)
- Latency stable (no degradation over time)
- Error rate <0.1% throughout
- Snapshot creation successful all 6 times, <30 seconds each
- Connection count stable (no leaks)
- Thread count stable
- File descriptor count stable
- GC pause times stable (<10ms p99)

**Expected Behavior:**
- Memory grows linearly due to event log accumulation
- Snapshot creation periodically resets event log
- After snapshot: Memory drops back to baseline
- CPU utilization remains constant
- GC frequency stable (not increasing)
- Latency distribution unchanged over 24 hours
- No resource leaks

**Failure Indicators:**
- Exponential memory growth (leak detected)
- OutOfMemory error
- Increasing CPU utilization over time
- Latency degradation (p99 increasing)
- Increasing GC frequency or duration
- Failed snapshot creation
- Connection count increasing
- Thread leaks detected
- File descriptor exhaustion

**Recovery Validation:**
- After 24 hours, stop load
- Verify system returns to idle state
- Memory released post-GC
- All resources cleaned up
- System ready for next operation
- No lingering state issues

### PT-005: Spike Test (Traffic Burst)

**Objective:** Validate system handles sudden 5x traffic spike, maintains stability during burst, and recovers quickly to baseline performance.

**Test Configuration:**
- Baseline: 100,000 orders/second
- Spike: 500,000 orders/second for 2 minutes
- Recovery: Return to 100,000 orders/second
- Pattern: Baseline (5 min) → Spike (2 min) → Recovery (5 min)
- Repeat: 3 cycles
- Measurement: Latency during spike, error rate, recovery time

**Performance Thresholds:**
- Baseline latency: <100μs p99
- Spike latency: <10ms p99 (acceptable degradation)
- Spike error rate: <10% (back-pressure may reject some orders)
- Recovery time: <30 seconds to baseline performance
- CPU spike: May reach 100%, but no sustained overload
- Memory spike: Bounded increase, then release

**Measurement Methodology:**
- Tool: Load generator with spike pattern
- Metrics: 1-second resolution for spike visibility
- Latency tracking: Continuous p99 measurement
- Error categorization: Back-pressure vs other errors
- Resource monitoring: Sub-second sampling during spike

**Pass Criteria:**
- System remains stable during spike (no crash)
- Spike latency <10ms p99
- Orders accepted or explicitly rejected (no silent failures)
- CPU returns to baseline <30 seconds after spike
- Memory returns to baseline after GC
- Error rate <10% during spike
- All subsequent operations normal after recovery
- No lingering performance impact

**Expected Behavior:**
- During spike: Latency increases, back-pressure activates
- Aeron publications return BACK_PRESSURED when buffers fill
- CPU utilization spikes to 100%
- Memory increases temporarily (queuing)
- After spike: Queued orders processed, system drains
- Latency returns to baseline within 30 seconds
- CPU utilization drops back to normal
- Memory released via GC

**Failure Indicators:**
- System crash during spike
- Sustained high latency after spike ends
- Memory not released after spike
- Continued high CPU after recovery period
- Silent order losses
- State corruption

**Recovery Validation:**
- Measure time to return to baseline p99 latency
- Verify all queued orders processed
- Check resource utilization returns to normal
- Validate no lingering errors
- Repeat spike to ensure consistent behavior

### PT-006: Aeron Back-Pressure Handling

**Objective:** Validate proper back-pressure behavior when Aeron publications fill, ensuring no data loss and graceful degradation.

**Test Configuration:**
- Simulate slow consumer by introducing processing delay
- Flood with orders to fill Aeron publication buffer
- Monitor publication offer() return codes
- Verify back-pressure propagation to clients

**Performance Thresholds:**
- Back-pressure detection: Within 1 second of buffer filling
- Orders: Queued or rejected appropriately (no silent drops)
- BACK_PRESSURED return code: Observed when buffer >80% full
- Recovery: System processes backlog when consumer catches up
- No data loss: All orders accounted for

**Measurement Methodology:**
- Tool: Custom test harness with Aeron metrics
- Monitoring: Aeron publication back-pressure counter
- Logging: Publication offer() return codes
- Verification: Order tracking from submission to execution/rejection

**Pass Criteria:**
- Back-pressure detected when buffer fills
- Publication returns BACK_PRESSURED status code
- Orders either queued (if space) or rejected with clear error
- No silent order drops (all orders traced)
- System recovers when consumer processes backlog
- No data corruption or loss
- Order sequence preserved (FIFO)

**Expected Behavior:**
- As buffer fills, offer() starts returning BACK_PRESSURED
- Gateway detects back-pressure, responds to client:
  - FIX: BusinessReject with "System busy"
  - REST: 503 Service Unavailable with Retry-After header
  - WebSocket: Error message with reason code
- Orders not accepted are not lost (client notified)
- When consumer catches up, back-pressure clears
- New orders accepted normally

**Failure Indicators:**
- Silent order drops (no rejection, no execution)
- System crash under back-pressure
- Unbounded memory growth
- Data corruption
- Out-of-order processing

**Recovery Validation:**
- Consumer catches up and processes backlog
- Back-pressure clears (counter stops incrementing)
- Subsequent orders accepted normally
- Latency returns to baseline
- No lingering issues
