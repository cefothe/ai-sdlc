## Output Directory

**IMPORTANT**: All QA artifacts are stored in the **PROJECT directory**, not the global ~/.claude/ directory.

All test documentation generated by this command should be saved to:
```
.claude/qa/<YYYYMMDD>-<feature-slug>/security-tests.md
```

Example: `.claude/qa/20251204-order-execution-flow/security-tests.md`

## Your Task

Generate comprehensive security testing scenarios covering authentication, authorization, input validation, rate limiting, API security, and protocol-specific security concerns for the feature described by the user.

## Test Types Argument

This command defaults to `--test-types=security` but can be overridden to include additional test types:

**Default:** `--test-types=security`
**Override examples:**
- `--test-types=security,functional` (add functional tests)
- `--test-types=all` (generate all test types)

## Input

The user will provide:
- Feature description or user story
- Security requirements (if specified)
- Authentication/authorization model (if specified)
- **Optional**: `--test-types` argument (defaults to `security`)

## Required Process

1. **Analyze Security Requirements**
   - Identify authentication mechanisms (JWT, session, API keys)
   - Determine authorization model (RBAC, permissions)
   - Assess input validation needs (injection attacks, XSS)
   - Identify rate limiting requirements
   - Evaluate protocol-specific security (FIX session auth, WebSocket auth)

2. **Create Output Directory**
   Create the project QA artifacts directory:
   ```bash
   FEATURE_SLUG=$(echo "$ARGUMENTS" | tr '[:upper:]' '[:lower:]' | tr ' ' '-' | sed 's/[^a-z0-9-]//g')
   OUTPUT_DIR=.claude/qa/$(date +%Y%m%d)-${FEATURE_SLUG}
   mkdir -p ${OUTPUT_DIR}
   ```

3. **Invoke the QA Principal Engineer Agent (Coordinator) - Plan Mode**

   **IMPORTANT**: The qa-principal-engineer will FIRST enter plan mode to create an execution plan.

   Use the Task tool to invoke the qa-principal-engineer agent:

   ```
   Analyze the following feature and create a comprehensive test generation plan:

   Feature: [Feature description]
   Test Types Requested: security (or from --test-types argument if provided)

   Requirements:
   1. Enter plan mode FIRST
   2. Parse test-types argument: security (default) or user-provided value
   3. Determine which agents to spawn (qa-security-engineer, and others if test-types includes them)
   4. Define scope for security testing:
      - Authentication testing (JWT, token expiration, session management)
      - Authorization testing (RBAC, permission boundaries, privilege escalation)
      - Input validation (SQL injection, XSS, command injection)
      - Rate limiting (per-IP, per-account, burst allowance)
      - API security (REST, WebSocket, FIX)
      - Session security (hijacking prevention, timeout enforcement)
      - OWASP Top 10 coverage
   5. Write execution plan to ~/.claude/plans/qa-execution-plan.md
   6. Exit plan mode for user approval
   7. After approval, spawn qa-security-engineer agent (and others if requested) with isolated context

   COVERAGE REQUIREMENTS:
   - Generate comprehensive security test coverage
   - No limits on test case count (generate ALL necessary scenarios)
   - Follow TEST_CASE_BEST_PRACTICES.yaml methodology
   - Test both positive (should allow) and negative (should block) cases
   - Reference specific codebase components

   OUTPUT DESTINATION:
   - Security tests: ${OUTPUT_DIR}/security-tests.md
   ```

4. **Invoke the QA Test Plan Reviewer Agent**
   Use the Task tool to invoke the qa-test-plan-reviewer agent:

   ```
   Review the security test scenarios created by the qa-principal-engineer agent.

   Evaluate across these critical dimensions:
   - Security Control Coverage (authentication, authorization, input validation)
   - Attack Vector Coverage (OWASP Top 10, injection attacks, session attacks)
   - Test Quality Standards (specific payloads, clear expected behavior)
   - Risk Assessment (critical vs high vs medium vulnerabilities)

   - Strategic Gaps (missing security controls, untested attack vectors)

   Provide:
   - Executive Summary with overall quality score (1-10) and critical blockers
   - Detailed Findings for each dimension with specific gaps
   - Missing Security Test Scenarios
   - High-Risk Vulnerabilities not adequately tested
   - Quality Gate verdict: APPROVED / APPROVED WITH CONCERNS / BLOCKED

   Read the security scenarios file at ${OUTPUT_DIR}/security-tests.md and provide specific, actionable feedback.

   Save your review to: ${OUTPUT_DIR}/security-tests-review.md
   ```

5. **Address Reviewer Findings**
   If the reviewer identifies issues (APPROVED WITH CONCERNS or BLOCKED):

   Use the Task tool to invoke the qa-principal-engineer agent again:

   ```
   Address the following issues identified by the qa-test-plan-reviewer:

   [List of specific issues from reviewer]

   Update the security scenarios to:
   - Add missing security test types
   - Enhance attack payload coverage
   - Address all CRITICAL and HIGH severity findings
   - Add missing OWASP Top 10 coverage
   - Improve expected secure behavior descriptions
   - Add missing protocol-specific security tests

   Update the security scenarios file at ${OUTPUT_DIR}/security-tests.md with the improvements.
   ```

6. **Final Review (if needed)**
   If significant changes were made, optionally invoke the reviewer again to validate improvements.

7. **Present Final Output**
   - Present the reviewed and improved security scenarios
   - Display the file location: `${OUTPUT_DIR}/security-tests.md`
   - Display the review location: `${OUTPUT_DIR}/security-tests-review.md`
   - Highlight the review verdict and quality score
   - Note critical security controls that received special attention
   - Call out any high-risk vulnerabilities to prevent

## Example Scenarios

### ST-001: JWT Token Expiration Enforcement

**Security Domain:** Authentication

**Attack Vector / Vulnerability:**
Expired JWT tokens should be rejected to prevent unauthorized access using old, potentially compromised tokens.

**Test Scenario:**
Validate that the REST API rejects requests with expired JWT tokens and returns appropriate error response without revealing sensitive information.

**Test Steps:**
1. Authenticate user and obtain valid JWT token:
   - POST /api/v1/auth/login
   - Credentials: test@omnius.com / correct_password
   - Extract JWT token from response
   - Note token expiration time (e.g., exp: 1 hour)
2. Use token immediately (should succeed):
   - GET /api/v1/positions
   - Header: Authorization: Bearer [valid_token]
   - Verify: HTTP 200 OK
3. Wait for token to expire (or manipulate system time)
4. Attempt to use expired token:
   - GET /api/v1/positions
   - Header: Authorization: Bearer [expired_token]
   - Verify: HTTP 401 Unauthorized
5. Check error response:
   - Verify error message does not leak sensitive info
   - Verify no system details in error
6. Verify audit log:
   - Failed authentication attempt logged
   - IP address, timestamp recorded

**Test Payloads:**
- Expired token: Token where `exp` claim is in the past
- Manipulated token: Change `exp` claim to future (should fail signature verification)

**Expected Secure Behavior:**
- Expired token rejected with HTTP 401 Unauthorized
- Error response: `{"error": "Unauthorized", "message": "Token expired"}`
- No sensitive information in error message
- No stack traces or system details leaked
- Request not processed (no side effects)
- Audit log entry: "Failed authentication: Expired token"
- User must re-authenticate to obtain new token

**Failure Indicators:**
- Expired token accepted (CRITICAL VULNERABILITY)
- Request processed with expired credentials
- Sensitive data returned
- Error message reveals token structure or secrets
- No audit log entry created
- System crash or exception

**OWASP Reference:** A02:2021 – Cryptographic Failures, A07:2021 – Identification and Authentication Failures

**Risk Level:** High

**Remediation (if fails):**
1. Implement token expiration validation in authentication middleware
2. Check `exp` claim against current time (with clock skew tolerance ±30 seconds)
3. Return HTTP 401 for expired tokens
4. Log failed authentication attempts
5. Implement token refresh mechanism for seamless user experience

### ST-002: Role-Based Access Control (RBAC) Permission Boundaries

**Security Domain:** Authorization

**Attack Vector / Vulnerability:**
Users should only access resources and perform actions authorized for their role. Prevent privilege escalation and cross-role access.

**Test Scenario:**
Create users with different roles (read-only, trader, admin) and verify that permission boundaries are enforced for order submission, position viewing, and account management operations.

**Test Steps:**
1. Create test users with different roles:
   - User A: Role = "read-only" (can view positions, cannot trade)
   - User B: Role = "trader" (can view positions, can trade)
   - User C: Role = "admin" (full access)
2. Authenticate as User A (read-only):
   - POST /api/v1/auth/login (User A credentials)
   - Extract JWT token
3. Test read-only user permissions:
   - GET /api/v1/positions → Should succeed (HTTP 200)
   - GET /api/v1/account → Should succeed (HTTP 200)
   - POST /api/v1/orders → Should FAIL (HTTP 403 Forbidden)
   - DELETE /api/v1/users → Should FAIL (HTTP 403 Forbidden)
4. Authenticate as User B (trader):
   - POST /api/v1/auth/login (User B credentials)
   - Extract JWT token
5. Test trader permissions:
   - GET /api/v1/positions → Should succeed (HTTP 200)
   - POST /api/v1/orders → Should succeed (HTTP 201)
   - DELETE /api/v1/users → Should FAIL (HTTP 403 Forbidden)
   - PUT /api/v1/config → Should FAIL (HTTP 403 Forbidden)
6. Authenticate as User C (admin):
   - POST /api/v1/auth/login (User C credentials)
7. Test admin permissions:
   - All endpoints → Should succeed
8. Attempt privilege escalation:
   - As User A, modify JWT role claim to "admin"
   - Attempt privileged operation
   - Verify: JWT signature invalid, request rejected

**Expected Secure Behavior:**
- Read-only user can view data, cannot modify
- Trader can view and trade, cannot administer
- Admin has full access
- Unauthorized actions return HTTP 403 Forbidden
- Error message: `{"error": "Forbidden", "message": "Insufficient permissions"}`
- No data leakage in error (don't reveal what permissions exist)
- Modified JWT rejected due to signature mismatch
- Audit log records permission denial attempts

**Failure Indicators:**
- Read-only user can submit orders (CRITICAL)
- Trader can perform admin functions
- Permission checks not enforced
- Modified JWT accepted (signature not verified)
- No audit log of permission denials
- Error message reveals permission structure

**OWASP Reference:** A01:2021 – Broken Access Control

**Risk Level:** Critical

**Remediation (if fails):**
1. Implement middleware to check user roles before processing requests
2. Define role-permission matrix clearly
3. Verify JWT signature before trusting claims
4. Return HTTP 403 for unauthorized actions
5. Log all permission denial attempts with details
6. Implement principle of least privilege

### ST-003: SQL Injection Prevention

**Security Domain:** Input Validation

**Attack Vector / Vulnerability:**
SQL injection allows attackers to execute arbitrary SQL commands, potentially exposing or modifying database contents. All user inputs must be sanitized or parameterized.

**Test Scenario:**
Attempt SQL injection attacks via various input fields (symbol search, order quantity, price) and verify that inputs are properly sanitized or parameterized to prevent SQL execution.

**Test Steps:**
1. Test SQL injection in symbol search:
   - GET /api/v1/symbols?search=EURUSD' OR '1'='1
   - Expected: Input sanitized, no SQL injection
   - Verify: Returns only matching symbols or empty
2. Test SQL injection in order submission:
   - POST /api/v1/orders
   - Payload:
     ```json
     {
       "symbol": "EURUSD'; DROP TABLE orders; --",
       "quantity": 100000,
       "orderType": "MARKET"
     }
     ```
   - Expected: Input validation rejects malformed symbol
   - Verify: HTTP 400 Bad Request, table not dropped
3. Test SQL injection in quantity field:
   - POST /api/v1/orders
   - Payload:
     ```json
     {
       "symbol": "EURUSD",
       "quantity": "100000; DELETE FROM positions; --",
       "orderType": "MARKET"
     }
     ```
   - Expected: Type validation rejects non-numeric quantity
   - Verify: HTTP 400 Bad Request, no data deleted
4. Test SQL injection in price field (LIMIT order):
   - POST /api/v1/orders
   - Payload:
     ```json
     {
       "symbol": "EURUSD",
       "quantity": 100000,
       "orderType": "LIMIT",
       "price": "1.08500' UNION SELECT password FROM users --"
     }
     ```
   - Expected: Price validation rejects malformed price
   - Verify: HTTP 400 Bad Request, no data leaked
5. Verify database integrity:
   - Query database: SELECT COUNT(*) FROM orders
   - Query database: SELECT COUNT(*) FROM positions
   - Verify: Tables intact, no data loss

**Test Payloads:**
Common SQL injection patterns:
- `' OR '1'='1`
- `'; DROP TABLE users; --`
- `' UNION SELECT password FROM users --`
- `1'; UPDATE accounts SET balance=999999 WHERE id=1; --`
- `' AND 1=0 UNION ALL SELECT 'admin', 'password' --`

**Expected Secure Behavior:**
- All SQL injection payloads rejected at input validation
- Parameterized queries used (no string concatenation)
- Input type validation enforced:
  - Symbol: Alphanumeric + limited special chars (A-Z0-9_-)
  - Quantity: Positive integer
  - Price: Positive decimal with correct precision
- Error response: HTTP 400 Bad Request
- Error message: `{"error": "Validation failed", "field": "symbol", "message": "Invalid format"}`
- No SQL error messages leaked to client
- No database modification from malicious input
- Audit log records malformed input attempts

**Failure Indicators:**
- SQL injection succeeds (CRITICAL VULNERABILITY)
- Database tables dropped or modified
- Sensitive data (passwords, account info) leaked
- SQL error messages visible to client
- Type validation not enforced
- String concatenation used in SQL queries

**OWASP Reference:** A03:2021 – Injection

**Risk Level:** Critical

**Remediation (if fails):**
1. Use parameterized queries or prepared statements ONLY
2. Never concatenate user input into SQL strings
3. Implement strict input validation with whitelists
4. Reject malformed inputs at API boundary
5. Use ORM frameworks that prevent injection by design
6. Apply least-privilege database permissions
7. Log all suspicious input patterns

### ST-004: Cross-Site Scripting (XSS) Prevention

**Security Domain:** Input Validation

**Attack Vector / Vulnerability:**
XSS allows attackers to inject malicious scripts into web pages viewed by other users, potentially stealing session tokens or performing actions on behalf of victims.

**Test Scenario:**
Attempt to inject JavaScript payloads into user-controllable fields (order comments, account names) and verify that outputs are properly sanitized to prevent script execution.

**Test Steps:**
1. Test XSS in order comment field:
   - POST /api/v1/orders
   - Payload:
     ```json
     {
       "symbol": "EURUSD",
       "quantity": 100000,
       "orderType": "MARKET",
       "comment": "<script>alert('XSS')</script>"
     }
     ```
   - Expected: Script tags sanitized or HTML-encoded
   - Retrieve order: GET /api/v1/orders/{id}
   - Verify: Comment returned as `&lt;script&gt;alert('XSS')&lt;/script&gt;` (encoded)
2. Test XSS in account name:
   - PUT /api/v1/account/profile
   - Payload:
     ```json
     {
       "displayName": "<img src=x onerror=alert('XSS')>"
     }
     ```
   - Expected: HTML tags stripped or encoded
   - Retrieve profile: GET /api/v1/account/profile
   - Verify: displayName = "alert('XSS')" (script removed)
3. Test XSS in symbol search:
   - GET /api/v1/symbols?search=<svg/onload=alert('XSS')>
   - Expected: Input sanitized, no script execution
4. Render outputs in web UI:
   - Load page displaying order comments
   - Verify: No JavaScript alert() executed
   - Verify: Scripts displayed as text, not executed
5. Test DOM-based XSS:
   - Manipulate URL parameters with XSS payload
   - Verify: Client-side validation sanitizes before DOM insertion

**Test Payloads:**
Common XSS patterns:
- `<script>alert('XSS')</script>`
- `<img src=x onerror=alert('XSS')>`
- `<svg/onload=alert('XSS')>`
- `javascript:alert('XSS')`
- `<iframe src="javascript:alert('XSS')"></iframe>`
- `<body onload=alert('XSS')>`
- `<input onfocus=alert('XSS') autofocus>`

**Expected Secure Behavior:**
- All HTML tags stripped or encoded
- JavaScript event handlers removed
- Output encoding applied (HTML entity encoding)
- Content-Security-Policy header prevents inline scripts
- X-XSS-Protection header enabled
- User input never inserted into HTML without sanitization
- DOM manipulation uses safe APIs (textContent, not innerHTML)

**Failure Indicators:**
- Script execution in browser (alert() or console.log() fires) - CRITICAL
- HTML tags rendered and executed
- No output encoding applied
- innerHTML used with user input
- No Content-Security-Policy header
- No input sanitization

**OWASP Reference:** A03:2021 – Injection (includes XSS)

**Risk Level:** High

**Remediation (if fails):**
1. Implement output encoding for all user-generated content
2. Use HTML entity encoding (< → &lt;, > → &gt;)
3. Strip HTML tags from user input (whitelist approach)
4. Set Content-Security-Policy header: `default-src 'self'; script-src 'self'`
5. Use safe DOM APIs (textContent, setAttribute, not innerHTML)
6. Implement input validation with whitelist of allowed characters
7. Enable X-XSS-Protection header

### ST-005: Rate Limiting Enforcement

**Security Domain:** API Security

**Attack Vector / Vulnerability:**
Absence of rate limiting allows attackers to flood the system with requests, potentially causing denial of service, brute-force attacks, or resource exhaustion.

**Test Scenario:**
Send requests exceeding configured rate limits and verify that the system throttles requests, returns appropriate HTTP status codes, and prevents resource exhaustion.

**Test Steps:**
1. Determine rate limit configuration:
   - Per-IP: 1000 requests/minute
   - Per-account: 500 requests/minute
   - Burst allowance: 50 requests/second
2. Test per-IP rate limit:
   - Send 1200 requests in 1 minute from single IP
   - Expected: First 1000 succeed, next 200 rejected
   - Verify: HTTP 429 Too Many Requests after limit
   - Verify: Retry-After header present (e.g., "60" seconds)
3. Test per-account rate limit:
   - Authenticate with account credentials
   - Send 600 requests in 1 minute
   - Expected: First 500 succeed, next 100 rejected
   - Verify: HTTP 429 with account-specific message
4. Test burst allowance:
   - Send 100 requests in 1 second (2x burst limit)
   - Expected: First 50 succeed, next 50 rejected or queued
   - Verify: Backoff enforced
5. Test rate limit reset:
   - Wait for time window to expire (e.g., 60 seconds)
   - Send new request
   - Verify: Rate limit reset, request succeeds
6. Test rate limit bypass attempts:
   - Change IP address (via proxy)
   - Use multiple accounts from same IP
   - Verify: Rate limits still enforced
7. Monitor system resources:
   - CPU, memory, network during rate limit enforcement
   - Verify: No resource exhaustion
   - Verify: System remains responsive

**Expected Secure Behavior:**
- Rate limit enforced accurately (±5% tolerance)
- HTTP 429 Too Many Requests returned after limit
- Retry-After header indicates when to retry
- Error response: `{"error": "Too Many Requests", "retryAfter": 60}`
- Rate limit resets after time window
- Multiple attempts from same IP counted together
- System resources protected (CPU <80%, memory stable)
- Legitimate traffic not affected
- Rate limit counters stored in fast cache (Redis)

**Failure Indicators:**
- Rate limit not enforced (requests always succeed) - HIGH RISK
- No HTTP 429 returned
- Missing Retry-After header
- Rate limit easily bypassed (IP change works)
- System resources exhausted under flood
- Legitimate users blocked incorrectly
- Rate limit counters inaccurate

**OWASP Reference:** A04:2021 – Insecure Design (lack of rate limiting)

**Risk Level:** High

**Remediation (if fails):**
1. Implement rate limiting middleware (e.g., Express rate-limit, Nginx rate limiting)
2. Use sliding window or token bucket algorithm
3. Store rate limit counters in fast in-memory cache (Redis)
4. Return HTTP 429 with Retry-After header
5. Implement per-IP and per-account limits
6. Configure burst allowance for temporary spikes
7. Monitor rate limit metrics (rejections, abuse patterns)
8. Consider adaptive rate limiting (lower limits for suspicious IPs)

### ST-006: FIX Protocol Session Authentication

**Security Domain:** API Security (Protocol-Specific)

**Attack Vector / Vulnerability:**
FIX protocol sessions must authenticate clients and validate message integrity to prevent unauthorized trading and message tampering.

**Test Scenario:**
Attempt to establish FIX sessions with invalid credentials, replayed logon messages, and out-of-sequence messages. Verify that the FIX gateway enforces session authentication and sequence number validation.

**Test Steps:**
1. Test valid FIX session establishment:
   - Send Logon (35=A) message with correct credentials
   - SenderCompID: CLIENT001
   - TargetCompID: OMNIUS
   - Password: correct_password
   - Expected: Logon accepted, session established
   - Verify: Logon response (35=A) received
2. Test invalid password:
   - Send Logon message with incorrect password
   - Expected: Logon rejected
   - Verify: Logout (35=5) with text "Invalid credentials"
   - Verify: Session not established
3. Test replay attack:
   - Capture valid Logon message (MsgSeqNum=1)
   - Wait for session to disconnect
   - Replay same Logon message (MsgSeqNum=1)
   - Expected: Rejected due to duplicate sequence number
   - Verify: Logout with "Duplicate sequence number"
4. Test sequence number validation:
   - Establish valid session (MsgSeqNum=1)
   - Send NewOrderSingle with MsgSeqNum=3 (skipping 2)
   - Expected: Gap detected, ResendRequest sent
   - Send messages out of order (3, 2, 4)
   - Verify: Session rejected or gap fill requested
5. Test message integrity:
   - Modify CheckSum field (10=XXX)
   - Expected: Message rejected, "Invalid checksum"
6. Test session timeout:
   - Establish session
   - Send no messages for >HeartBtInt + 30 seconds
   - Verify: Logout due to inactivity

**Expected Secure Behavior:**
- Valid credentials required for Logon
- Invalid credentials rejected with Logout
- Sequence numbers validated (monotonically increasing)
- Gaps detected and ResendRequest triggered
- Duplicate sequence numbers rejected (replay prevention)
- CheckSum validated on every message
- Session timeout enforced (no stale sessions)
- Logout on any authentication or integrity failure
- Session state tracked per client

**Failure Indicators:**
- Invalid credentials accepted (CRITICAL)
- Replay attack succeeds (sequence not checked)
- Out-of-order messages processed
- Invalid CheckSum ignored
- Session never times out
- No audit log of failed logon attempts

**OWASP Reference:** A07:2021 – Identification and Authentication Failures

**Risk Level:** Critical

**Remediation (if fails):**
1. Implement FIX session authentication (SenderCompID + password)
2. Validate sequence numbers strictly (MsgSeqNum)
3. Detect and reject duplicate sequence numbers
4. Request ResendRequest for gaps
5. Validate CheckSum on every message
6. Implement heartbeat and timeout logic
7. Log all logon attempts (success and failure)
8. Consider TLS for FIX connections (FIXS)
